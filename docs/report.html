Mini Inference Router: technical report

A small LLM gateway with a customer-support assistant on top. The gateway authenticates each tenant, holds a dollar budget, routes Haiku 5.5 → Sonnet 5.5 → a backup, and records every attempt. The assistant answers from a knowledge base and refuses rather than guess.

Stack: one Node 22 service (Fastify, TypeScript), Postgres, a React console. Deployment: live at mini-inference-router.onrender.com (Render free tier in Singapore, Neon Postgres, demo mode). Video: a narrated walkthrough of the live console, on Google Drive. Tests: 30 integration and unit tests, plus a 9-step browser walkthrough against the real models.

  • Retrieval is what makes the answers right.Without the knowledge base, Haiku's answers pass the judge 20 of 35 times; with it, 34 of 35. All 14 disagreements favour retrieval.
  • Sonnet adds nothing measurable over Haiku here, at 20× the cost.Identical outcomes on all 35 cases. So Haiku goes first, and Sonnet is kept for availability.
  • The eval can't be gamed by near-duplicates.A random split of this dataset lets retrieval alone score 97–100%. The held-out cases here have every close copy removed from the knowledge base.

How a request flows

Every request passes the same gateway checks. The support assistant adds retrieval before the model and an intent check after it.

Routing and fallback

Cheapest model first, a fallback only before the customer sees any text, and every attempt recorded.

Haiku 5.5 $0.10 / $0.50→ Sonnet 5.5 $2 / $10→ Backup $0, stored answer

Each tenant has an ordered list of allowed backends. A request walks it, skipping any backend whose circuit is open. Prices are per million input / output tokens.

What one fallback looks like

Haiku 5.5 sent nothing within its time limit (52 ms) Sonnet 5.5 first token 760 ms, done 1,963 ms

A real request from the slow-haiku demo tenant, whose Haiku limit is set to 50 ms. Hatched: waiting for the first token. The console shows this trace for every request.

Circuit breaker. After 3 failures in a row a backend is skipped for 30 s; the next failure after that re-opens it. Two kinds of failure don't count, because either would let one tenant switch a model off for everyone: timeouts forced by a tenant's own settings (the demo tenants), and 400 errors, which a caller can provoke with a malformed chat.

No hidden retries. The Anthropic SDK runs with retries off. Retrying is the router's job; silent retries would distort latency and defeat the first-token timeout.

Quota and metering

The budget is in dollars, reserved before each model call and settled after, so it can't be overspent, even under concurrency.

Why dollars, not tokens: Sonnet costs 20× Haiku and the two count tokens differently, so a token budget would mean different things depending on who served.

1. Check

Before streaming, the tenant's first-choice model must fit the remaining budget. If not: HTTP 429.

2. Reserve

Each attempt reserves its worst case (input + max output, at that model's price) in one conditional UPDATE that only succeeds if it fits.

3. Settle

When the attempt ends, the reservation is swapped for the actual cost, from token counts the provider reports in the stream.

  • Atomic: a test fires 25 reservations at once at a budget that fits 10, and exactly 10 succeed. With the guard removed, the test fails.
  • Fails closed: if the database is unreachable, the request gets a 503 instead of being served without metering.
  • Honest numbers: if a stream breaks before the final token count, output is estimated (characters ÷ 4) and flagged as estimated. Cost is "estimated" because it comes from the price table, not an invoice.

Two endpoints

The raw chat endpoint is the gateway itself; the support endpoint is an app built on it.

POST /v1/chat

  • Takes a whole conversation (up to 20 messages); the server keeps no state
  • Passes it to the model as-is; any non-empty reply is accepted
  • Up to 1,024 output tokens

POST /v1/support/chat

  • Takes one customer message
  • Adds retrieval, the support prompt, the intent check, confidence and refusal
  • Up to 600 output tokens

Both share auth, budget, routing, metering and streaming. Keeping them apart shows the gateway works for any app, and makes failures easy to place: if raw chat works and support doesn't, the problem is in retrieval, not routing.

The support assistant

Retrieval finds similar past questions, the model must name an intent before it answers, and it refuses when the two don't back each other up.

  • Knowledge base: 1,998 deduplicated question–answer pairs from the Bitext dataset, 74 per intent, searched with BM25 (MiniSearch). Common English words are ignored and the top-5 vote is weighted by score: 90.6% intent accuracy on its own (dev slice), up from 86.5% for plain BM25. No embeddings: the questions are short paraphrases, and word matching already gets about 90%.
  • Intent first: the model's reply must open with <intent>label</intent>, one of 27 labels or out_of_scope. The gateway holds the stream until it parses, so a bad header can still fall back to the next model.
  • Placeholders: template slots like {{Order Number}} are filled from a demo store profile, and a filter catches any that leak into the answer.

Catches what slips past retrieval, like "tell me a joke about cats"

Not confident

One or none of the 5 retrieved answers carry the model's intent.

Confidence: 4–5 agree = high, 2–3 = medium, 0–1 = low

Does the confidence signal mean anything?

Yes. On the 297-question dev slice (no model calls), the more of the top 5 that agree, the more often retrieval is right:

Model choice

Haiku 5.5 to answer, Sonnet 5.5 for when Haiku is slow or down, and a backup for when both are.

  • Haiku 5.5 is fast and cheap (about $0.0002 per answer) and reports exact token usage in the stream.
  • Sonnet 5.5 has its own rate-limit pool, so it covers Haiku being rate-limited, overloaded or slow.
  • The backup returns the closest stored answer. It exists because both models share one API key: a revoked key, a spend limit or an Anthropic outage takes both down at once.
  • Both models run with thinking off at effort low; a short grounded answer gains little from it. Haiku takes thinking: disabled; Sonnet 5.5 rejects that and needs between_tools. No sampling parameters are sent.

A deliberate deviation. The challenge allows "a local model, a provider free tier, or both". This build uses a paid key instead, for exact usage reporting, a full eval run for about $1, and a deployment that doesn't need a local GPU. Per-tenant budgets and a low spend limit on the key cap what a public URL can cost.

Evaluation

30 held-out questions plus 5 off-topic ones, four configurations, and one result that clearly isn't noise.

Why these numbers can be trusted

  • No near-copies: questions are deduplicated, and a held-out question must be less than 0.8 similar (cosine, character 3–5-grams) to every knowledge-base question. A naive split would let retrieval score 97–100% by finding a copy.
  • Tuned elsewhere: thresholds were set on a separate 297-question dev slice. The eval has 27 cases (one per intent) plus 3 keyword-style ones, and 5 hand-written off-topic questions.
  • Small-sample honesty: every accuracy has a 95% interval, and configurations are compared case by case (exact McNemar test), not just by headline rate.
  • The judge is Claude Opus 5.5, a different and larger model, scoring three yes/no checks: addresses the request; invents nothing; refusing or answering was right. It sees the store's reference answers so it can tell grounded facts from invented ones.

What the numbers say

  • Retrieval is what makes the answers right.All 14 cases where the two Haiku runs disagree favour retrieval (p ≈ 0.0001). Without it, 10 answers invented store policy ("no cancellation after shipping") and 5 deflected ("see the checkout page") instead of giving the store's actual options. Intent barely moved (28 vs 29 of 30): the model can classify on its own, but can't answer correctly for this store.
  • Haiku against Sonnet is a null result, and an expected one.Retrieval sets confidence, decides refusal and supplies the facts; the model only labels and words the answer. The two produce identical outcomes on all 35 cases. Sonnet costs 20× more and adds about 400 ms to the first token.
  • On intent, the model ties retrieval.Haiku's extra correct label is a case it then refused, so counting answers actually given, both get 28 of 30. What the model measurably adds is catching all 5 off-topic questions, against 2 for retrieval alone.
  • The one false refusal is a typo."deleting Business accoumt": the model labelled it correctly, but the typo broke retrieval, so only 1 of 5 entries agreed and the confidence rule refused it. The rule stays: one false refusal in 30 is the price of not trusting a model that is confidently wrong.

Checking the checker

The first judge didn't see the reference answers and failed about 30% of answers for "inventing" the store's phone number and hours, which were in fact in the references. It was changed to see them and both models were rerun. A hand check of 10 judged cases, both failures included, read against the same references and marked before seeing the judge's verdict, agreed with the judge on all 10. Ten cases can catch a judge that is badly off, not a small bias. Reading the first judge's fails also turned up one real defect, an unfilled template slot showing as text, fixed before the rerun.

End to end: npm run e2e drives the console in a real browser against the server, Postgres and both models, and records a video: normal answer, both kinds of refusal, fallback to Sonnet, the backup serving, raw chat, the budget failing closed, a bad key, and the stored trace in the usage view. All 9 steps pass.

Trade-offs and cuts

A smaller system that is measured, and a list of what was left out on purpose.

Accepted

  • Fallback only before the first token. A mid-stream failure ends as "incomplete" rather than retrying, because the customer has already seen the text.
  • Word-matching retrieval. Cheap and good enough here; it misses paraphrases that share no words.
  • In-memory breaker and index. Fine for one instance; several would each keep their own breaker.
  • Single-turn support. A follow-up like "what about the fee?" would need rewriting into a full question before retrieval, an extra model call per turn.
  • Free hosting. Render's free tier sleeps after 15 idle minutes; the first request after that is slow.

Cut

  • Tenant management UI (tenants come from a seed script)
  • Monthly budget periods
  • Per-minute rate limits
  • Embeddings and a vector database
  • Multi-turn memory for support
  • Mid-stream recovery
  • Login (an opt-in demo mode hands out demo keys instead)
  • Prompt caching (the prompt is about 1,100 tokens)
