# Mini Inference Router

A small LLM gateway with one capability on top: a customer-support assistant over the Bitext dataset.

- **Gateway:** per-tenant API keys, a fail-closed cost quota, and metering of every request to Postgres. Answers stream over SSE.
- **Routing:** Claude Haiku 5.5 first, Claude Sonnet 5.5 as the fallback, and an extractive mock as the last resort. Every attempt is recorded and can be inspected.
- **Support assistant:** BM25 retrieval over a 2,000-row knowledge-base slice. It returns the answer, the intent, the retrieved entries and a confidence signal, and it refuses instead of guessing.
- **Console** (React): guided scenarios, a plain-language verdict and a route trace for every request, and a per-tenant usage view.
- **Eval:** 30 held-out cases plus 5 out-of-domain ones, run against two configurations.

Live demo: <https://mini-inference-router.onrender.com>. It runs on Render's free tier, so the first request after an idle spell can take about a minute.

Video walkthrough (3:57, narrated): <https://drive.google.com/drive/folders/1ErYy5O2lBSbiwoHwWzQaevZ9MB3SSdXO?usp=sharing>.

## Run locally

You need Node 22+ and a Postgres. Docker is the easiest way to get one.

```bash
docker run -d --name mir-pg -e POSTGRES_PASSWORD=mir -e POSTGRES_DB=mir -p 55432:5432 postgres:17-alpine
```

```bash
npm ci && npm run build
```

Create `.env` with:

```
DATABASE_URL=postgres://postgres:mir@localhost:55432/mir
ANTHROPIC_API_KEY=sk-ant-...      # optional: without it, Anthropic attempts fail and the mock serves
ADMIN_TOKEN=change-me
```

```bash
npm run seed
```

```bash
npm run dev
```

The seed prints one API key per demo tenant. Open http://localhost:3000. The Playground takes a tenant key and the Usage view takes the admin token.

For a demo, start with `DEMO_MODE=1 npm run dev` instead. The console then picks the tenant for each scenario itself and the Usage view needs no token. Anyone who can reach the URL can spend the demo tenants' quotas, so it's off by default.

```bash
curl -N http://localhost:3000/v1/support/chat -H "Authorization: Bearer <tenant key>" -H "Content-Type: application/json" -d '{"message":"how do I cancel my order?"}'
```

### Demo tenants

| Tenant | Route | Shows |
|---|---|---|
| `acme` | Haiku → Sonnet → mock | The normal path |
| `slow-haiku` | Haiku (50 ms first-token timeout) → Sonnet → mock | A real timeout falling back to Sonnet |
| `outage` | Haiku (50 ms) → Sonnet (50 ms) → mock | The last resort serving |
| `flaky-mock` | mock (50% failure, 800 ms) → Haiku | Configurable failure and latency |
| `tiny` | Default route, $0.0005 quota | Quota failing closed with a 429 after the first request |
| `eval-haiku`, `eval-sonnet` | One backend each | The two eval configurations |
| `mock-only` | mock | Offline development, and the retrieval-only baseline |

## Tests

```bash
npm test
```

The tests need the local Postgres. They use the database `mir_test`, which you create once with `docker exec mir-pg psql -U postgres -c "create database mir_test"`. Model backends are scripted, so the tests never call a real model.

```bash
npm run typecheck
```

### Browser E2E (records a video)

```bash
npx playwright install chromium
```

```bash
npm run e2e
```

It seeds the database, starts its own server in demo mode on port 3000 (stop any server already there), and drives the console through 9 scenarios. It calls the real models, so it needs `.env` with `ANTHROPIC_API_KEY` and costs a few cents. The video lands in `test-results/`.

## Eval

```bash
npm run eval -- --key <eval-haiku key> --name haiku
```

```bash
npm run eval -- --key <eval-sonnet key> --name sonnet
```

```bash
npm run eval -- --compare eval/results/haiku.json eval/results/sonnet.json
```

For the retrieval ablation, start a second server with `PORT=3001 SUPPORT_RETRIEVAL=off`, and run the eval with `--base http://localhost:3001 --name haiku-no-retrieval`. That server sends the model no reference answers, and it's for the eval only.

The judge (Claude Opus 5.5) runs when `ANTHROPIC_API_KEY` is set. Pass `--no-judge` to skip it, and `--base <url>` to run against the deployed service.

## Data

`data/` is a slice of the [Bitext customer support dataset](https://huggingface.co/datasets/bitext/Bitext-customer-support-llm-chatbot-training-dataset) (see its dataset card for the licence), generated by `scripts/make_split.py` from the Bitext CSV, with a fixed seed. It deduplicates the questions and holds out only those whose closest knowledge-base match is below cosine 0.8, so the eval can't be answered by looking up a near-copy. `scripts/tune.ts` sets the out-of-domain threshold using the dev slice only.

## Deploy

`render.yaml` describes one free Render web service in Singapore with `DEMO_MODE=1`, so reviewers can click through the console. Set `DATABASE_URL` (Neon, pooled connection string) and `ANTHROPIC_API_KEY` in the Render dashboard. Render generates `ADMIN_TOKEN`. Run the seed once against the Neon database before the first deploy, since demo keys are issued at boot for tenants that already exist:

```bash
DATABASE_URL=<neon url> npm run seed
```

The live service was created by hand as a web service from the public repo, with the same settings as `render.yaml`, not as a Blueprint. Pushes don't deploy on their own: use Manual Deploy → Deploy latest commit in the Render dashboard.

The free plan sleeps after 15 idle minutes and takes about a minute to wake. An external pinger (UptimeRobot, cron-job.org) hitting `/` every 10 minutes keeps it up. Ping `/`, not `/healthz`: `/healthz` queries the database and would keep Neon's free compute from ever suspending. For the same reason Render's own health check uses `/`.
